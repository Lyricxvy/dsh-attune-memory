## 第一部分：项目概况

### 1.1 项目定位

dsh-attune-memory 是 DeepSeek Harness（DSH）的长期记忆插件，由两部分组成：

- **插件**（`plugin/dsh-attune-memory/lib/`，Node ESM）：挂到 DSH 的 `systemPrompt` 与 `agent/pre-step` 上，负责"把这轮该知道的记忆塞进上下文"以及"把该记的东西写进去"。
- **引擎**（`engine/attune_memory/`，Python 3.11 纯标准库 + SQLite）：负责存储、检索、生命周期、可解释性，通过 stdio JSON-RPC 由插件以常驻子进程方式驱动（`plugin/dsh-attune-memory/lib/engine.js`）。

它的目标不是"保存聊天记录"，而是维护一份可持续纠正的 **User Model** 与 **Interaction Model**：谁、在做什么、希望被怎么帮。这一目标在 v1.0 设计书（现归档于 `01-架构设计与技术决策/`）里就已确立，v0.3.0 没有改变它。

### 1.2 v0.3.0 的主要目标

v0.3.0 **不新增用户可见功能**，它的目标是修"看不见的坏"：

| 目标 | 具体所指 |
|---|---|
| 写入要准 | 不是所有话都配进长期记忆；工位状态、文件里能查到的、一次性安排、否定句式都要挡在门外 |
| 数据要整 | 物理删除不能留半个状态；`update`/`merge` 不能绕过校验；多用户/高精度时间下不变量仍成立 |
| 规模要扛 | 写入从 O(n²) 降到接近线性；检索不再"只查最近 200 条" |
| 时间要分 | 记忆要有"现在/过去/一次性/不确定"的时间维度，失效要区分"记错了"与"事实变了" |
| 冲突要判 | 只有真正互斥才取代；同一句话换个说法就地改，不制造并列条目 |
| 状态要可观测 | 一条记忆从候选到被模型看到，每一段都要有计数；读路径不能再顺手写库 |

对应 6 个阶段、20 个工作包、2 个贯穿验证包（`02-版本实施与执行记录/DSH_v0.3.0_IMPLEMENTATION_PLAN.md` §三）。

### 1.3 本次版本建设范围

- **在范围内**：阶段 0（基线冻结）→ 阶段 5（可观测性），以及 V1-5 验证体系（四道闸、规模基准、外部对照工具）。
- **明确不在范围内**：Raw-history RAG、MCP Server、语义（Embedding）检索、人工审核队列。前两项在计划书 §六 里被划到 v0.4.0，后两项属于更远的版本（v0.3.0 计划 §七"功能边界"）。

### 1.4 版本意义

v0.2.0 解决的是"契约在五个地方各写一遍"（SSOT、启动自检、端到端穿透）。v0.3.0 往下一层走：**把"我们以为它可靠"变成"有对照基线、有失败样例、有可复算数字"**。

具体地说，这个版本第一次让项目具备了：

1. 一份**冻结的旧版本基线**（同一引擎指纹、同一数据、同一 K）与新版对照；
2. 一套**四道闸**（契约/场景/判分器/规模），把"自测全绿"拆成可分别失败的四件事；
3. 一份**外部评测的行为记录**，包括"新版哪里变差了"。

但也要说清楚：**这些仍然是自证**。外部基准全部标 `UNVERIFIED`，85 道退化题只有归因没有逐题复算（第五、六部分）。

## 第三部分：核心技术改进

每项按"原有问题 → 设计思路 → 实际实现 → 验证方式 → 效果与局限"组织。所有代码路径均已核对当前源码。

### 3.1 写入准入与职责分层

**原有问题**：任何一句话都可能被模型写进长期记忆。真实使用中出现过"本窗口在忙什么"被当成用户偏好、"README 里写了什么"被重复记录、一次性安排（"明天上午十点提醒我"）占住记忆槽位。更糟的是否定句式："不考数学一了"会被检索成"考数学一"的近义句。

**设计思路**：在价值判断（这条好不好）之前，先做三类**确定性**排除——它们判的不是质量，而是"这类东西根本不该进长期记忆"。规则必须可枚举、可测试、不依赖模型。

**实际实现**（`engine/attune_memory/write.py:664` `intent_gate`，词表在 `engine/attune_memory/const.py`）：

1. 运行时状态：`RUNTIME_MARKERS`（本窗口/这个窗口/本会话/这轮/本任务/当前对话…）→ 拒。
2. 可从文件验证：`FILE_VERIFIABLE_PATTERNS`（协作看板/协作看板/STATUS.md/README/package.json/cordis.patch.yml/git log/commit/分支/仓库/工作区/目录结构/配置文件/源码/接口文档/schema）→ 拒。
3. 一次性安排：`ONE_OFF_PATTERNS`（明天/后天/今晚/下周/下个月/待会儿…）→ 拒。
4. 否定极性：`不|取消|没有 + NEGATION_STATE_VERBS`（考/启用/开启/保留/加上/必须/使用）→ 拒；但句内出现 `CORRECTION_MARKERS`（改考/改成/准备/决定…）时放行，交给冲突决策表。

`explicit=True` 不豁免这三类（用户说"记住，我在这个窗口负责记忆分析"依然不该进库）。

**验证方式**：`tests/test_v030_stage1.py` 15 例（R-1.1.1~R-1.3.3），覆盖四类拒绝、explicit 不豁免、丢弃日志与计数。

**效果与局限**：

- 效果（已验证）：这四类确实被挡住了，且在 `metrics().counters` 里能看到 `intent_rejected`。
- **局限（本次实测复现，重要）**：规则按**子串**匹配，会误杀稳定偏好。实测（`engine` 目录下）：

  ```
  用户偏好：仓库里每个 commit 都要写 scope   → ignore（命中「commit」）
  用户喜欢先拉分支再改，不直接动 main        → ignore（命中「分支」）
  用户不使用 emoji                          → ignore（否定句式）
  ```

  后两条是**真实的长期偏好**，却被"可从文件验证"与"否定极性"两条规则挡掉。这不是理论风险，是可复现的误拒。详见第六部分 §6.1。

### 3.2 task scope 的实现及其作用

**原有问题**：跨窗口/跨任务污染——"这次先用表格回答"变成永久偏好，下次写文案也带着表格。

**设计思路**：给记忆加一个"任务键"，属于某任务键的记忆只在同一任务里参与注入，不进稳定层。

**实际实现**：

- 引擎：`store.query(task_key=)` 用 `json_extract(metadata,'$.task_key')=?`（不用 `LIKE`，避免 `task_key=A` 命中 `AB`）；`search.build_candidates()` 里 `if not task_key or metadata.task_key != task_key → 丢弃`（`engine/attune_memory/search.py:253`）；`read.stable_items()` 显式跳过 `scope=="task"`。
- 插件：`recall.js:258` 把 `task_key` 固定成 `` `session:${sessionId}` `` 并传给 `read_for_context`；`tools.js` 的 `memory_remember` 支持 `task_key`，缺省用 `hooks.taskKey()`（`index.js:97`）即当前会话。

**验证方式**：`tests/test_v030_stage1.py` 的 task scope 用例（写入带 task_key、无匹配键时不注入、`stable_items` 不含 task 记忆）；插件侧由 `recall.test.mjs` 间接覆盖。

**效果与局限**：

- 效果（已验证）：`scope=task` 的记忆不会出现在稳定块，也不会在别的 session 注入。
- **局限**：`task_key` 目前等价于 `session:<sessionId>`，所以它解决的是**会话级隔离**，不是"任务级"。同一个任务跨两个会话（比如今天开一个窗口、明天再开一个）时，昨天那条 task 记忆今天注入不出来。命名与语义有落差，见 §6.2。

### 3.3 数据一致性、事务处理与数据库维护

**原有问题**：①`purge` 曾是"删流水 + 删主行"两段，中途失败会留下半个状态；②`update`/`merge` 不经过写入口校验，能绕过枚举与主体约束；③不变量检查不分用户，一个用户的历史条目会让另一个用户报"多 active"；④时间只有秒级，`add` 后立刻 `supersede` 落在同一秒，as-of 边界不可分。

**实际实现**：

- `write.purge()`：先查是否被别的条目 `superseded_by` 指向（断链拒绝），再在**单个 `store.tx()`** 里写 `action="purge"` 的 tombstone 流水、删倒排、删主行。`memory_change` 保留（审计链）。
- `write.update()`：把"合并后的整行"重新构造成 Candidate 过 `validate()`；`valid_until<=now` 时同时 `set_status(...,"archived")`。
- `store.verify_invariants()`：按 `user_id` 分组；取代链目标必须同 user；单值槽位检查从 `state` 扩到 `profile/identity` 与 `domain/decision`；新增倒排完整性（active 记忆无索引项 / 孤儿索引项）。
- `util.fmt_iso()`：定宽毫秒 `YYYY-MM-DDTHH:MM:SS.mmmZ`，`now_iso()` 统一走它；`parse_iso()` 兼容旧秒级。

**验证方式**：`tests/test_v030_stage2.py`（purge 回滚、断链拒绝、update 归档、merge 校验、倒排一致性、毫秒序）；`TestOpsRegistry`（op 注册表一致性）。

**效果与局限**：

- 效果（已验证）：中途异常时事务整体回滚（测试用连接代理注入 `Boom` 验证）；`verify_invariants()` 在 183 例测试的混合写入后返回空。
- 局限：`purge` 的"断链"判断只看 `superseded_by` 一处，不检查 `metadata.merged_from` 之类软引用；目前没有用例覆盖"被 merge 的源条目先被 purge"。

### 3.4 检索候选集与索引性能优化

**原有问题**（本版本最重要的工程发现）：

1. `build_candidates()` 用 `ORDER BY updated_at DESC LIMIT 200` 取候选。库里有 3 万条时，这 200 条永远是"最近写的"，与问题词无关；相关的旧记忆根本不进候选。
2. 写入路径上 `near_keywords()` 对每个 term 扫整条倒排链（正文模板里的"要点/独立"每条都有），单题入库 3–6 分钟。

**设计思路**：写入侧按 df 选入口词，公共词走"最近优先"扫描而不是倒排链；检索侧反过来——**按查询词查倒排**取候选，再补少量最近写入兜底。

**实际实现**：

- 写入（`store.near_keywords`）：每个 term 只取 df 最小的 gram 作入口；`COMMON_DF=200` 以上改走 `idx_mem_updated`；`instr()` 校验下推到 SQL；`MAX_POSTING=5000`。
- 检索（新增 `store.candidates_by_terms`，`engine/attune_memory/store.py`）：`SELECT memory_id, COUNT(DISTINCT gram) FROM memory_gram WHERE user_id=? AND gram IN (...) GROUP BY memory_id ORDER BY c DESC LIMIT 200`，df>200 的公共 gram 不进 `IN`；`search.build_candidates(terms=...)` 有查询词时走它，再补 `RECENT_FILL=50` 条最近写入（领域约定等无词面重合的记忆仍需在场）。
- 配套：`same_slot(limit=30)`、`count_slot()` 报真实槽位总数、`find_similar` 槽位切片。

**验证方式**：

- `eval/bench_write_scale.py`：500/1000/2000/5000 条写入，per-write 增长 **1.43×**（门槛 <3.0），5000 条 **21.8s**（上限 120s）。
- 回归用例 `R-2.3.5`：501 条库里，200 条噪声 + 1 条相关事实，`search` 必须命中（修前命中 0）。
- 外部基准：LongMemEval `haystack=0` R@5 **10.0% → 27.5%**；`haystack=20` **42.5% → 77.5%**；LoCoMo **13.4% → 24.4%**（第五部分）。

**效果与局限**：

- 效果（已验证）：候选集从"时间窗"变成"词面命中优先"，外部基准三处全部不劣化，两处显著提升。
- **局限**：`MAX_CANDIDATES=200` 仍是硬上限，候选集换了之后必然有题"一升一降"——LoCoMo **85 题变差（4.3%）**就是代价（§5.4）。另外新候选集让"多词但都不精确"的查询更容易挤进 200 条，长会话下 gold 被挤出窗口的风险仍在。

### 3.5 记忆时态与生命周期治理

**原有问题**：记忆没有时间维度。"我之前在 A 公司"与"我现在在 A 公司"同形；过期状态仍进稳定块（每轮重发比检索不到更危险）。

**实际实现**：

- 四字段：`temporal_kind`（current/historical/event/uncertain）、`event_date`（仅 event）、`last_verified`、`invalidation`。
- `search(asof=...)`：切到"当时的视图"，`valid_from <= asof < valid_until`；status 取 active/superseded/archived。
- `read.stable_items()` 过滤 `is_expired`（修 #48）。
- `tick()`：只做两条自动转换——state 过期 7 天后归档、superseded 满 180 天归档；不做自动遗忘/合并/降权。
- 迁移：`ensure_columns()` + `migrate_data()`，旧 `superseded` 回填 `invalidation='superseded'`（不猜 corrected）。

**验证方式**：`tests/test_temporal.py` 14 例（四列与索引存在、老库迁移不丢数据、非法枚举拒绝、event_date 仅 event、as-of 返回历史事实、过期不进稳定块、迁移幂等）。

**效果与局限**：

- 效果（已验证）：as-of 能查到历史事实，corrected 在任何视图都不召回，过期 state 不进稳定块。
- **局限**：迁移把所有历史行标 `current`，且不回填 `last_verified`/`valid_until`。一条 2025 年写的"用户正在备考数学一"如果当时就没设 `valid_until`，迁移后仍是 current，会被稳定块继续注入。**这一点没有测试覆盖**，见 §6.4。

### 3.6 corrected 与 superseded 的区分

**原有问题**：v0.2.0 只有 `superseded` 一个出口，把"原来记错了"和"事实变了"混在一起。前者不该再出现在任何视图（它本身是错的），后者应该留在时间轴上（as-of 查得到）。

**实际实现**：

- `_commit_supersede`：`invalidation='corrected'` → 旧条 `status='archived'`；否则 `'superseded'`。两者都写 `valid_until=now`、`superseded_by=新 id`。
- `search.build_candidates()`：`invalidation=='corrected'` 一律丢弃（注释写明"连 as-of 也不行——当时那条本身是错的"）；`superseded` 在 `asof` 视图里保留。
- `explain().state_reason`：superseded 会给出"已被 X 取代（何时起失效）：原因"。

**验证方式**：`tests/test_temporal.py` 的"corrected→archived 且 as-of 不召回"用例；`explain` 的 `state_reason` 由 `engine/tests/test_engine.py` 的 explain 相关用例覆盖（阶段 3 没有单独的 `test_v030_stage3.py`，其测试并入 `test_temporal.py`）。

**效果与局限**：

- 效果（已验证）：两条路径行为不同且可解释。
- **局限**：`status='archived'` 被两种语义共用（corrected 的旧条、过期归档、180 天归档）。区分只能看 `invalidation` 字段；`explain()` 对 archived 的文案统一写"不再参与检索与注入"，而"superseded 满 180 天归档"的行其实在 as-of 下仍可召回。文案与语义有轻微不一致（§6.3）。

### 3.7 冲突识别、极性判断与事实更新规则

**原有问题**：①`same_slot` 太粗，同一科目不同分数被当成冲突；②极性词判断把"我不喜欢先给结论"记成"喜欢先给结论"（真实缺陷 #33）；③用户把同一句话换个说法说一遍，就多出一条并列记忆。

**实际实现**：

- 属性级关键值：`search.key_values()` 返回 `{属性: 取值}`（版本/路径/端口/数值/分数/中文数量），`_exclusive()` **只比同名属性**——数学 120 与英语 120 不冲突，数学 120 与数学 130 冲突。
- 极性：`POLARITY_PAIRS` 12 对（需要/不需要、支持/不支持、考/不考…），明确不含"是/不是"。
- 措辞修正：`write._lcs_ratio(a,b)` ≥ 0.92 且无关键值冲突 → 就地 `store.update_fields(action="update")`，不新增条目。
- 三档取代：显式且 conf≥0.8 自动 supersede；0.6–0.8 并存并写 `metadata.conflict_with`；<0.6 丢弃并计数 `supersede_low_confidence`。推断（`explicit=False`）永不自动取代。

**验证方式**：`tests/test_v030_stage4.py` 6 例（同科目不同分不互斥、同属性不同分取代、identity 单值槽位被抓、"支持/不支持"取代、"某专业课"不被过滤、措辞修正就地 update、换科目是新增、关键值变化不算措辞修正）。

**效果与局限**：

- 效果（已验证）：措辞修正不再制造并列条目；跨科目同分不打架。
- **局限**：LCS 0.92 是启发式。"用户正在备考数学一"与"用户正在备考数学二"的 LCS 也接近 0.9，只因关键值/科目词不同才没被合并——如果一句改写既改了关键事实又保持高相似度，仍可能被当成措辞修正就地覆盖。测试只覆盖了少数几对，见 §6.5。

### 3.8 可观测性指标和只读查询路径

**原有问题**：只记 `inject_count`/`use_count` 两个数，看不出"这条记忆从候选走到模型眼前"的哪一段断了；读路径还会写 `use_count`（正反馈 + 读放大成写）。

**实际实现**：

- 计数（`memory_counter`）：`candidates_total`、`intent_rejected`、`gate_rejected`、`op_add/touch/supersede/merge`、`search_candidates`、`search_hits`、`inject_items`、`inject_chars`、`rpc_errors`、`supersede_low_confidence`、`type_hint_suspected`。
- 观测（`memory_observation`）：`kind='read'`（前 80 字查询 + 候选/命中/注入/丢弃原因）、`kind='discarded'`（被丢弃候选前 120 字 + 理由，保留 14 天，可 `purge`）。
- `metrics()` 信封：`schema/version/started_at/coverage/funnel`。
- 读只读：`search(count_use=False)` 默认不写；`read_for_context` 不写；`stable_block` 的计数已删（它每 step 重算）。

**验证方式**：`tests/test_v030_stage5.py` 11 例（六态字段齐全、render/deliver 随读增长、metrics 信封、started_at 稳定、读不写 use_count、显式 count_use 生效、read_for_context 不写、读不改 updated_at）；插件 `recall.test.mjs` 12 组覆盖 `inject_expected/inject_visible/faded_*` 上报。

**效果与局限**：

- 效果（已验证）：引擎侧的 candidate/generated/rendered 有计数且被测试断言；读路径确实不再写库。
- **局限 1**：`used` 没有生产者——`grep -rn "counter_bump(" engine/attune_memory/*.py` 里没有任何 `"used"`，`metrics().funnel.used` 恒为 0。
- **局限 2**：`delivered`（`inject_expected`）与 `visible`（`inject_visible`）由插件回报，跨进程 headless 场景下 `#lastInject` 不保留，核对只能靠插件单测；真机只有 12 组断言与契约测试的 `memory_counter` 行作为证据。
- **局限 3**：`rendered`（引擎 `inject_items`）与 `delivered`（插件 `inject_expected`）来自不同进程的两次计数，同一轮里二者通常相等，但没有恒等断言。

### 5.3 必须说明的口径边界

1. **这不是 LongMemEval 500 题全量评测**。只取了 `--n 20` 的 20 道题（按题目类型分层抽样，`seed=20261119`）。20 题的置信区间约 ±10pp，只能当方向性证据。
2. **迷你池（haystack=20）不能与论文全量基准直接比较**，它是"每题只保留 20 个 session"的缩小池，分数天然更高。
3. **完整 haystack 的 20 题评测**是每题 39–66 个 session、约 1700 个块、合计 34592 条入库——这个配置更接近"真实长历史"，但 20 题不足以支撑"LongMemEval 达到 X%"这类结论。
4. **指标是 A-R 检索召回**（答案 session 是否排进前 K），**不是端到端问答质量**。模型能否答对不在本指标内。

## 第六部分：存在的问题与技术局限

以下按审查重点逐条给出判断，**不代表预设它们必然存在缺陷**。每条给证据与状态。

### 6.1 文件可验证规则可能误拒稳定偏好 —— **成立（本次实测复现）**

`FILE_VERIFIABLE_PATTERNS` 是子串匹配，包含 `仓库`、`分支`、`commit`、`源码`、`配置文件`、`schema`、`README`、`package.json`。任何包含这些词的用户偏好都会被拒：

```
用户偏好：仓库里每个 commit 都要写 scope   → ignore（命中「commit」）
用户喜欢先拉分支再改，不直接动 main        → ignore（命中「分支」）
用户不使用 emoji                          → ignore（否定句式）
```

**这是真实误拒**，因为后两条是稳定的 Interaction Model 事实，正属于系统最该记的东西。复现命令：`python -c "from memory.manager import Memory; ..."`（见 §3.1）。

**附带发现（新，未列入审查清单）**：`memory_preview` 与 `memory_add` 的结论不一致。`write.preview()` 只走 `validate()` + `value_gate()`，**不调用 `intent_gate()`**（`engine/attune_memory/write.py` 中 `preview` 函数体可核对），所以同样的内容：

```
preview → would=add
add     → ignore（intent_gate 命中）
```

这意味着模型按 S1 手册"先 preview 再决定"时，会得到错误预期。严重度中等，但会直接误导写入决策。

### 6.2 全局记忆与 task scope 是否解决跨窗口污染 —— **部分成立**

- 已解决：`scope=task` 的记忆不进稳定块、跨会话不注入（代码 + 单测）。
- 未解决：`task_key` 实际取值是 `session:<sessionId>`，所以"任务"= "会话"。真正的多窗口同一任务（今天开、明天再开）不会共享 task 记忆；反过来，同一会话里不同子任务共享一个 task_key，隔离粒度也不对。
- 另外，"全局记忆 vs task"的分界完全取决于模型在写入时是否标 `scope=task`，而 S1 手册对此只有一句提示（`read.MANUAL`），没有强制规则。

**状态：部分验证 / 设计意图与实现语义有落差。**

### 6.3 corrected、superseded、archived 的语义一致性 —— **基本一致，但状态字段被复用**

- 区分靠 `invalidation`（corrected/superseded/NULL），不靠 status；`build_candidates` 对 corrected 一律丢弃，与 as-of 也一致。
- 问题：`status='archived'` 同时表示"被纠正的旧条""过期归档的 state""满 180 天的 superseded"。三者语义不同，只能靠 `invalidation` 与 `reason` 反推。
- `explain().state_reason` 对 archived 统一输出"不再参与检索与注入"，但"superseded 满 180 天归档"的行在 as-of 下**仍可召回**，文案与行为有轻微不一致。

**状态：已验证（行为一致）/ 部分验证（可读性）。**

### 6.4 旧记忆迁移为 current 可能让过期信息继续被召回 —— **风险成立且无测试覆盖**

`migrate_data()` 只做两件事：把空 `temporal_kind` 填成 `current`，把旧 `superseded` 填 `invalidation='superseded'`。它**不推断** `valid_until`，也不回填 `last_verified`。

后果：一条 2024 年写下的"用户正在备考数学一"、当时没有设置有效期，迁移后仍是 `current`，会继续进稳定块。这与 v0.3.0 引入时态治理的初衷相反。

**状态：已实现（迁移）/ 未验证（风险场景）/ 无测试。**

### 6.5 LCS 相似度规则可能误合并不同事实 —— **部分成立**

`_wording_fix` 的触发条件是"同槽位 + LCS≥0.92 + 非互斥 + 同名关键值不冲突"。它不会跨槽位合并（换科目是不同槽位，会走新增），所以"数学一 vs 数学二"这类不会误合并。

但同一槽位内的高相似改写仍可能吞掉语义差异，例如"用户正在备考数学一（2026 年 12 月初试）"与"用户正在备考数学一（2027 年 12 月初试）"——年份不是 `key_values` 抽取的关键值（只抽版本 `\d+\.\d+`、路径、端口、数值+单位、分数、中文数量），所以可能被判成措辞修正就地覆盖。

**状态：部分验证（现有 6 例未覆盖年份/日期类差异）。**

### 6.6 检索候选集优化的潜在副作用 —— **成立，已知 85 题退化**

见 §5.4。另外两个潜在副作用没有测试：

- `MAX_CANDIDATES=200` 把"多词但都不精确"的查询也放进来，可能挤掉精确命中；
- `RECENT_FILL=50` 的兜底会把最新 50 条无条件带入候选，若这些恰是与查询无关的新数据，会稀释 top-K。

**状态：已验证（总体提升）/ 未验证（副作用边界）。**

### 6.7 六态是否都有实际证据 —— **不成立（缺 used）**

### 6.8 外部基准是否足以支持复现 —— **部分可复现**

- 足以：数据哈希、引擎指纹、参数、逐题预测、判分脚本都在；当前源码指纹与 post 运行一致。
- 不足：基线快照已丢失（§5.5）；`report.py` 的口径修复没有单测，若有人用旧版本重算会得到 1.7% 这类错数；判分逻辑本身没有第三方复算。

## 第七部分：版本范围调整

### 7.1 Raw-history RAG 与 MCP Server：未实现

- 计划书 §六 把 `W-R1 原始历史索引`、`W-R2 语义检索管线`、`W-R3 词法打分退役`、`W-R4 证据与事实冲突仲裁`、`W-R5 MCP Server 解耦` 列为 "v0.4.0 预规划，本版不实施"。
- 实际核对：`grep -rln "mcp\|embedding\|sentence_transformers" engine/attune_memory engine/eval` → 无结果；插件 `lib/` 也无 MCP 入口。
- 因此这两项**不是 v0.3.0 的交付成果**，不能计入本版本完成度。

### 7.2 原架构目标与本次范围的关系

`DSH_MEMORY_ARCHITECTURE_DESIGN_VNEXT.md`（20 章）的总体目标是 **Hybrid Memory**：结构化事实层 + 原始历史检索层（RAG）+ 治理与可观测，三者协同。v0.3.0 只做了"结构化事实层"的可靠性与可观测，**没有做原始历史检索层**。

用一句话概括当前状态：**词法 + 结构化的记忆系统已经可靠、可解释、可观测；它仍然答不了"问题用词与原文不重合"的那类题**（第五部分失败样例：`How many shirts did I pack…`、`total distance…` 全部召回为空）。这正是 v0.4.0 的动机，也是不能把"外部基准提升"解读为"记忆能力已经够用"的原因。

### 7.3 范围调整的时机与理由

- 阶段 0 的基线暴露了"词法检索在完整 haystack 下接近随机"（R@5 10% vs 随机 10.1%），这件事如果在 v0.3.0 内解决，就等于提前做 v0.4.0 的 RAG，会破坏"先稳地基、再换引擎"的顺序。
- 因此把 RAG 留在 v0.4.0，v0.3.0 只做"让现有词法检索不被自己的候选集坑死"（§3.4）。这个取舍写在计划书 §七 与 `06` 节的本汇报中，属于**有意识的范围控制**，不是延期。

## 第九部分：总体评价

### 9.1 本版本最有价值的成果

**不是某个功能，而是"可对照、可复算"这件事第一次成立。**

具体是两样东西：

1. **一份冻结基线 + 一套对照工具**（`lme-baseline-full` / `compare.py` / `gates.py`）。它让"新版是不是变差了"从主观判断变成一条命令。本次正是靠它抓到了两个真实缺陷（`report.py` 口径错误、检索候选集只取最近 200 条），其中后者在 3 万条库上会让相关记忆完全不可达。
2. **写入准入与时态治理**把"该不该记"和"什么时候失效"变成了有代码路径、有测试、可解释的状态机，而不是全靠模型自觉。

### 9.2 哪些改进真正提高了系统可靠性

按证据强度排序：

1. **检索候选集走倒排**（§3.4）：外部基准三处全部不劣化、两处大幅提升，且有 501 条库的确定性复现用例。这是本版本最硬的一项。
2. **purge 单事务 + update/merge 统一校验**（§3.3）：消除了"半个状态"与"绕过校验"两类结构性风险，有回滚测试。
3. **读路径只读 + 稳定块不再每 step 写库**（§3.8）：去掉了一条每轮都发生的写放大。
4. **时态四字段与 as-of**（§3.5）：让"过时"第一次可表达，though 迁移口径偏保守（§6.4）。

### 9.3 哪些问题仍然限制实际记忆能力

1. **误拒**：`intent_gate` 会挡掉含"仓库/分支/commit"等词的稳定偏好；`preview` 与 `add` 结论不一致（§6.1）。这是当前最该优先修的写入缺陷。
2. **词法天花板**：外部失败样例里，问题与原文不重合时召回直接归零（§7.2）。这不是参数问题，是架构问题，只能靠 v0.4.0 的原始历史检索。
3. **task scope 名不副实**：实际粒度是会话（§6.2）。
4. **可观测性半截**：`used` 没有生产者；`visible` 只在插件单测里有证据（§6.7）。
5. **迁移风险**：老数据一律 `current`，没有时效推断（§6.4）。

### 9.4 值得保留的技术决策

- **命中闸门卡 `Relevance × Confidence × ContextMatch`，不卡最终分**：否则 `importance=normal` 或过期条目会静默消失（v0.3.0 之前的教训，本次继续保留）。
- **只做两条自动转换（过期归档、180 天归档），不做自动遗忘/合并/降权**：不可逆动作一律留给人。
- **三档 supersede**：显式高置信才自动取代，中置信并存并标注冲突，低置信丢弃并计数。
- **单库 + 查询期视图**：不为 User Model 建副本表（约束 A 的落地判定仍是"删掉所有副本，行为不变"）。
- **评测工具拒绝不可比**：参数/数据哈希不一致直接退出，不允许"看起来差不多"的对照。
- **外部基准强制 UNVERIFIED + 附 predictions**：把"自测"这件事写进产物，而不是靠人记。

### 9.5 为后续迭代留下了什么

- **v0.4.0 的入口已经清楚**：失败的 5 个样例都是"问题用词与原文不重合"，指向原始历史检索（RAG），而不是继续调词法权重。
- **可复算的对照链**：只要保留 `predictions.jsonl` 与 `run.json`，任何后续版本都能和 v0.2.0 / v0.3.0 对比；基线快照丢失的问题可以用"把冻结源码归档进仓库"来根治（尚未做）。
- **可观测出口**：`metrics()`、`reads()`、`discarded()` 三个只读出口已经就位，v0.4.0 换检索层时可以用它们验证"注入是否真的到达模型"。

### 9.6 一句话结论

**v0.3.0 把"记忆系统的地基"做完了：写入有准入、数据有事务、检索有索引、时间有维度、冲突有判据、状态有计数；但它既没有改变"词法检索的天花板"，也没有真正发布——运行中的 DSH 仍是 v0.2.0。** 从工程角度这是一次合格的加固版本；从产品角度，它还没有回答"记忆到底有没有让人少重复交代"这个问题（该问题需要真实使用 1–2 周的行为数据，本版本未采集）。
