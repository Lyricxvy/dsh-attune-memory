## W-0.1 LongMemEval 完整 haystack 基线跑

**任务 ID**：W-0.1 ｜ **阶段**：0 ｜ **V1 项**：V1-0 ｜ **台账**：#38 ｜ **优先级**：P0 ｜ **前置**：无 ｜ **后续**：W-0.2、阶段 1-5 全部 ｜ **影响范围**：仅 .ext-runs/ 产物，不改代码。

### 1. 背景与目标
改造前（Raw-history RAG 之前）必须冻结当前词法检索的实际表现，作为后续所有阶段"是否劣化"的对照。首轮 lme-auto 用了 --n 20 --haystack 20（每题只保留 20 session 的迷你池，K=20 时 random baseline≈100% 不可读），不作数。本包用完整 haystack（--haystack 0，每题 39-66 session）跑出可读基线。

### 2. 当前实现
评测入口 engine/eval/external/run.py（灌数据+取排名）、report.py（判分）、benchmarks.py 的 longmemeval_shards()。数据 .ext-dl/longmemeval_s（278MB，500 题，每题独立 haystack 39-66 session，已确认非共享池）。引擎写入 O(n²)（search.py find_similar → store.py near_keywords 全表扫），完整 haystack 单题 3-6 分钟。

### 3. 目标设计
输入：longmemeval_s 数据 + 当前引擎。输出：.ext-runs/lme-baseline-full/ 的 run.json + predictions.jsonl + ingest.json + report.md（STATUS=UNVERIFIED）。

### 4. 实施步骤
1. 在 engine/ 目录跑：python -m eval.external.run --bench longmemeval --data ../.ext-dl/longmemeval_s --n 20 --haystack 0 --k 20 --keywords bow --seed 20261119 --out ../.ext-runs/lme-baseline-full
2. 跑完后判分：python -m eval.external.report --run-dir ../.ext-runs/lme-baseline-full --bench longmemeval --data ../.ext-dl/longmemeval_s
3. 读 report.md，记录 R@5/R@10/R@20/Hit/random baseline/分类型。
预期：20 题约 1-2 小时；report.md 生成且 STATUS=UNVERIFIED。

### 5. 边界与异常
完整 haystack 单题入库超时（>10 分钟/题）→ 是 O(n²) 已知瓶颈，如实记录耗时，**不要改引擎**。命令报错 → 记录完整 stderr 返回，不擅自改脚本。

### 6. 测试设计

命令见 §4；在 engine/ 目录运行；依赖 Python 3.11（<DSH_INSTALL>\python\python.exe 已在 PATH）。成功判据：report.md 生成、STATUS=UNVERIFIED。出错定位：看 ingest.json 的 elapsed_s 与 stderr 尾行。

## W-1.1 写入意图准入门

**任务 ID**：W-1.1 ｜ **阶段**：1 ｜ **V1 项**：V1-2 ｜ **台账**：#46/#47 + 工作安排审查 ｜ **优先级**：P0 ｜ **前置**：W-0.2 ｜ **后续**：W-1.2 ｜ **影响范围**：engine/attune_memory/write.py、plugin/lib/extract.js、plugin/lib/index.js。

### 1. 背景与目标
当前没有"这条该不该进长期记忆"的确定性闸门，工作安排/协作配置/运行时状态被当成事实写入（工作安排审查 Q1-Q7 的 A-E 五条）。目标：写入前加确定性排除规则，让"可从文件验证/含上下文指代/一次性安排"在写入口就被拒绝。

### 2. 当前实现
engine/attune_memory/write.py 的 validate()（只查枚举合法）和 value_gate()（write.py:263，价值闸门）；engine/attune_memory/const.py 已有 TRANSIENT_PATTERNS/TASK_PATTERNS/QUESTION_PATTERNS/ANAPHORA 词表（write.py 管线里用作瞬态/任务/提问过滤）。plugin/lib/extract.js 与 index.js 的 extractAndStore 做兜底抽取。**缺**：可从文件验证→拒绝、一次性安排→拒绝、否定极性→修正不记反 这三条确定性规则。

### 3. 目标设计
在 value_gate() 之前加一个意图准入门 intent_gate(cand)，三条确定性排除规则：
1. 可从文件验证（subject_name 或 domain_key 命中项目文档/状态文件信号）→ 拒绝返回 WRITE_SKIPPED；
2. 含上下文指代（const.ANAPHORA 命中且无法脱离上下文读）或一次性安排 → 拒绝；
3. 否定极性（const.POLARITY_PAIRS 含"不/别/取消"等）→ 修正极性，不记反向事实。
抽取侧（plugin/lib/extract.js）同步加这三条，保证兜底抽取与显式写入口径一致。

### 4. 实施步骤
1. 在 write.py 新增 intent_gate(cand)（放 value_gate 之前调用）；2. 复用 const.ANAPHORA/POLARITY_PAIRS；3. 新增 const.FILE_VERIFIABLE_PATTERNS（如"协作看板/状态文件/仓库/README"等信号词）；4. extract.js 同步调用同一规则（跨语言，用一致词表）；5. 落库跳过计数进 memory_counter。

### 5. 边界与异常
缺失数据（content 空）→ validate 先拦；否定句（"不考数学二"）→ 修正为考数学一的正向表述或跳过；指代词（"本窗口"）→ 拒绝并提示改写；纯用户偏好（"报告写完整"）→ 不得误拦（不含指代/文件信号，应放行）。

## W-2.1 purge 单事务

**任务 ID**：W-2.1 ｜ **阶段**：2 ｜ **V1 项**：V1-7 ｜ **台账**：#12/#36 ｜ **优先级**：P0 ｜ **前置**：W-1.3 ｜ **后续**：W-2.2 ｜ **影响范围**：engine/attune_memory/write.py:697。

### 1. 背景与目标
物理删除（purge）当前是「记流水→删流水→删记忆」三步裸操作，非原子：中途崩溃会留下「流水删了记忆还在」或「记忆删了流水还在」的不一致（#12），且不留 tombstone（#36）。

### 2. 当前实现
engine/attune_memory/write.py 的 purge()（write.py:697）：先 update_fields()（内部有 tx，记 purge 流水），再裸 conn.execute 删 memory_change，再裸 conn.execute 删 memories。后两步不在 tx 内，且删掉 memory_change 后审计链断裂。

### 3. 目标设计
purge 三步包进单一 store.tx()；保留 tombstone（memory_change 里的 purge 流水不删，作为 tombstone 保留）；物理删记忆行，但流水保留供审计。

### 4. 实施步骤
1. store.py 调整：purge 时不再删 memory_change，改保留 purge 流水作为 tombstone；2. write.py purge() 用 with store.tx() 包住「记流水 + 删记忆」两步；3. 删 memory_change 的逻辑移除。

### 5. 边界与异常
purge 非 deleted 状态 → InvariantError（现有，保留）；purge 时进程中断 → tx 回滚，两步都不生效；memory_change 已不存在 → 跳过，继续删记忆。

### 6. 测试设计
| 用例 | 输入与前置 | 操作 | 预期 | 断言 |
|---|---|---|---|---|
| R-2.1.1 | 记忆 status=deleted | purge | 记忆删、tombstone 留 | 记忆 0 行 + 流水含 purge |
| R-2.1.2 | 记忆 status=active | purge | 拒绝 | InvariantError |
| R-2.1.3 | purge 中途注入异常 | purge | 回滚 | 记忆仍 deleted、流水完整 |

### 7. 命令与验证
engine/：python -m unittest tests.test_engine -v。验证：R-2.1.1~2.1.3 全绿。

### 8. 迁移与回滚
无 schema 迁移。回滚：purge 逻辑整体回退。

### 9. 完成标准

## W-2.2 merge/update 统一走 validate + 生命周期

**任务 ID**：W-2.2 ｜ **阶段**：2 ｜ **V1 项**：V1-7 ｜ **台账**：#13/#35/#22 ｜ **优先级**：P0 ｜ **前置**：W-2.1 ｜ **后续**：W-2.3 ｜ **影响范围**：engine/attune_memory/write.py:570、write.py:626。

## W-2.3 写入索引优化（O(n²) → 近线性）

**任务 ID**：W-2.3 ｜ **阶段**：2 ｜ **V1 项**：V1-7 ｜ **台账**：#38 ｜ **优先级**：P0 ｜ **前置**：W-2.2 ｜ **后续**：W-2.4 ｜ **影响范围**：engine/attune_memory/store.py:176、search.py:367。

### 1. 背景与目标
find_similar（search.py:367）每次写入都调 store.py:176 的 near_keywords()，后者「SELECT * FROM memories WHERE user_id=? AND status='active'」全表扫 + Python 侧逐条子串匹配，无索引 → n 次写入 × O(n) = O(n²)。这是 LongMemEval 完整 haystack 单题 >3 分钟、500 题 >25 小时的直接根源（#38 缺规模基准暴露）。

### 2. 当前实现
store.py:176 near_keywords()：全表 SELECT + 「any(t in hay for t in terms)」。search.py:367 find_similar() 对每个 add 调 near_keywords（terms+kws 最多 16 词）。

### 3. 目标设计

# V1-3 Raw-history RAG 检索（v0.4.0 预规划，本版不实施）

> 说明：V1-3 已由哥哥拍板（证据层=c 全量检索覆盖，DSH 只存索引不存原文，宿主持有原文），但工程量大、依赖 MCP Server 解耦与 embedding 基础设施，归入 v0.4.0。此处仍按「七项 V1 逐项展开」要求给出工作包规划，实施时再细化到 RUNBOOK 十段粒度。

## W-R1 原始历史索引（embedding + 定位，不存原文）

**目标**：对宿主会话历史建 embedding 索引 + 定位信息（message_id/offset），DSH 不复制原文。前提：宿主提供可靠历史读取、增量同步、删除同步接口（哥哥拍板的 c 方案前置条件）。
**验收**：索引覆盖全部历史；宿主删除原文后索引同步失效；索引与原文生命周期一致。

## W-R2 语义检索管线（召回 + 混合 + 重排序 + 过滤）

**目标**：Raw-history RAG 语义召回证据片段（主力）+ 结构化事实检索（辅助）；混合 BM25/倒排兜底（待实验）；重排序按时间/实体/领域/事实状态过滤；corrected/过期不进上下文。
**验收**：LoCoMo/LongMemEval A-R 召回显著高于当前词法 13.4%（H2 假设验证）。

## W-R3 词法打分退役（结构化记忆检索退居辅助）

**目标**：search.py 六因子词法打分管线退役，结构化记忆只做稳定块注入 + memory_search 显式查询 + 结构化过滤；relevance/recency/importance 简化。
**验收**：检索主力切换后稳定块注入不劣化；旧六因子代码移除。

## W-R4 证据与事实冲突仲裁（旧事实不覆盖当前事实）

**目标**：检索到的证据片段（可能是旧原文）与结构化事实（带时态）冲突时，结构化事实优先表达当前状态，证据并列标注差异，不强制二选一（约束 C）。
**验收**：旧地址/新地址并存时，模型看到当前状态 + 历史原文，不误用旧值。

## W-R5 MCP Server 解耦（宿主依赖的根本解法）

**目标**：Memory Core 抽成独立 MCP Server，标准化历史读取/身份映射/上下文投递接口（哥哥拍板采纳，但只解决接口不解决宿主数据读取本身）。
**验收**：Memory Core 不依赖某宿主内部实现；宿主切换不需改 Core。
