## 0. 版本定位与范围（项目负责人自行拍板的决策）

### 0.1 版本主题

**v0.3.0 = 结构化记忆正确性**（把现有记忆系统"做对"）：时态治理、职责分层、数据一致性、冲突判据、可观测性。

**不在 v0.3.0**：Raw-history RAG 检索收敛 + MCP Server 解耦（它们是检索路线重构 + 宿主解耦，工程量大且依赖新基础设施，单独开 **v0.4.0**）。

对应关系：设计书「V1 必需 7 项」= 下一个大阶段；v0.3.0 = 其中 6 项（V1-0/1-2/1-7/1-1/1-4/1-6）；v0.4.0 = 剩 1 项（V1-3 检索收敛，含 MCP Server）。

### 0.2 A/B 决策（原「20 题先行 vs 先优化引擎」）

**选 A：20 题完整 haystack 先行出基线，O(n²) 优化作为 v0.3.0 阶段 2 的正式任务，不提前。**

理由：①「冻结基线」的本意是记录**改造前**表现，先优化引擎会让基线不纯，无法区分"召回提升来自检索方案改进还是引擎优化"；②O(n²) 优化本身是台账 #38 + 设计书 V1-7 的正式内容，应作为 v0.3.0 的一部分有序做，而非为跑基线而临时做；③20 题完整 haystack 的 random baseline 可读（非 100%），已可作为改造前参照。

### 0.3 基线口径（固定，冻结）

- LoCoMo：13.4%（bow，已冻结，.ext-runs/locomo-bow/，引擎指纹 c14bd981，UNVERIFIED）。
- LongMemEval-S：--n 20 --haystack 0 --keywords bow --seed 20261119 --k 20（完整 haystack，20 题）。
- 两个基线共同构成「改造前」检索表现参照，后续每个阶段以它们为对照。

### 阶段 2：数据一致性 + 规模（V1-7，治 #12/#13/#35/#22/#37/#30/#38）
- **任务 4** 事务收口：purge 单事务（软删+物理删+tombstone 原子）；merge/update 统一走 validate + 生命周期；verify_invariants 按 user_id 分组；高精度时间。
- **任务 5** 写入索引优化（O(n²)→近线性）：find_similar 的同一 slot 线性查重改为确定性索引（subject 分组 + 倒排/哈希）；补规模基准 500–5000 块。

### 阶段 3：时态治理（V1-1，治 #57/#48/#49 时态部分）
- **任务 6** temporal_kind 四态（current/historical/event/uncertain）+ invalidation 二分（corrected/superseded）+ 三时钟分离（event_date/last_verified）+ valid_until 对任意可失效类型开放。
- **任务 7** 迁移脚本：新字段默认值兼容旧库（temporal_kind=current、invalidation=None）；现有 status=superseded 回填 invalidation 类型（保守标 superseded）。
- 验收：过期不注入、纠正后旧值 0 复活、as-of 查询正确；迁移幂等可回滚。

### 阶段 4：冲突判据（V1-4，治 #49/#11/#10/#33）
- **任务 8** 确定性判据：同槽位（subject_type+subject_name+属性 key）才互斥；极性词表；时态类型冲突优先级。

- 验收：同槽位多值 active 消除（#11）；措辞修正不 supersede（#49）；否定偏好不记反（#33）。

### 阶段 5：可观测性（V1-6，治 #52/#54/#53/#24）
