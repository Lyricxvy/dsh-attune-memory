## 1.2 交叉分析：五部分如何相互印证、补充、冲突

（这是本设计书的方法核心。以下每一条「交叉」都说明：哪些资料在哪一点上互相印证或冲突，以及它如何改变判断。）

### 交叉 1：台账「内容正确性」三连 ↔ Anima 时态治理（最强印证）

- **台账证据**：#57「系统擅长判断结构完整性，却缺『内容现在是否仍为真』的持续校验」（P0）、#48「多条 active 记忆已过期却标为长期有效」（P0）、#49「真正的事实变更未触发 supersede，措辞修正反而触发」（P0）。三条都是生产数据反例，不是架构推测。
- **Anima 机制**：temporal_kind（current/historical/event/uncertain）+ invalidation（corrected/superseded）+ 三时钟分离（occurrence/observation/validity）。
- **印证关系**：台账的反例，正是 Anima 这套字段设计要消灭的问题。DSH 现在只有 status=superseded 一种失效态，无法区分「纠正错误」与「正常更新」，无法表达「一次性事件」与「历史事实」。
- **判断改变**：把「时态治理」从 Anima 报告里的「建议 1」升格为**新架构的第一优先级必需项**——因为它有生产数据背书，不再只是外部参照。

### 交叉 2：台账「检索路线」 ↔ LoCoMo 实测（互为因果）

- **台账证据**：#42「检索路线处于高复杂度、低验证的中间地带」（P0）、#32「relevance 词表命中被广播给所有候选」（P0）、#17「候选上限按 updated_at 截断，重要旧记忆进不了检索」（P0）、#50「domain_key 漂移致漏召回」（P0）、#51「auto_keywords 产生垃圾关键词」（P1）。
- **LoCoMo 实测**：A-R 检索 R@5 = 9.9%（auto）/ 13.4%（bow），时间类 cat3 仅 4.3%；比随机基线高 6–10 倍（证明链路在按内容匹配），但绝对值仍低（证明纯词法匹配对不上题型）。
- **印证关系**：台账说「高复杂度、低验证」，LoCoMo 就是那个缺失的「验证」；实测结果反过来证明台账的判断成立——六个乘数因子 + 三阶段管线，最终只换来 13.4% 召回。
- **判断改变**：检索路线必须**收敛**——方向是「放弃手写词法打分、转向 Raw-history RAG」（详见交叉 7），而不是在 FTS5/倒排/embedding 之间继续挑。「先基准」仍然成立：以 LoCoMo/LongMemEval 为裁判，但裁判的对象是「Raw-history RAG vs 手写词法」的召回对比。

### 交叉 3：台账「职责混层」 ↔ Dreaming 的 consolidate vs DSH 的 compose（路线确认）

- **台账证据**：#46「语义判断、投递逻辑与治理职责混层，局部补丁不断绕回新缺陷」（P0 宏观根因）、#47「长期记忆库被运行时状态污染，task scope 零使用」（P0）。
- **Dreaming 结论**：ChatGPT 走 consolidate-at-rest（写入期后台综合），DSH 走 compose-at-read（读时组合，ADR-004）。两条相反路，DSH 不应照搬后台自动综合。
- **印证关系**：#47 的「污染」本质是「没有把『长期事实』和『任务/运行时状态』分开」——这既是职责分层问题，也是「读时组合」路线下必然要补的准入门。Dreaming 报告说「不值得借鉴后台自动综合」，反过来支持「把分层做在写入口，而不是靠后台整理补救」。
- **判断改变**：新架构用「证据层 / 事实层 / 组装层」三分法解决 #46，用「写入意图准入门」解决 #47；后台综合（Dreaming）明确留 V2 且有触发条件，不进 V1。

### 交叉 4：三份外部资料 + 台账，共同指向「时态正确性」这一缺口

- **Dreaming**：官方三维 eval 里「随时间正确」（9.4→52.2→75.1%）是提升最陡、也最贴近真实价值的维度；
- **Anima**：整套 temporal 模块（三时钟、五种查询、失效二态）就是为时态正确性而建，且有测试覆盖；
- **LoCoMo**：cat3 时间类 R@5 仅 4.3%，是 DSH 检索最弱的题型——「什么时候/多久」这类问题，词法匹配根本对不上；
- **台账**：#48/#57/#27（tick 无自动调度）全是时态/新鲜度问题。
- **判断**：时态正确性不是某个模块的附属功能，而是**贯穿证据层、事实层、组装层的横切关注点**。

### 交叉 5：三份资料共同强调「测试全绿 ≠ 能力可靠」（验证立场收敛）

- **台账**：#39「验证体系靶子错位，证明能跑多于证明跑得对」（P0）、#43「文档与 ADR 的论证能力明显强于经验验证」（P1）、#31「测试覆盖作者预设路径」（P1）；
- **LoCoMo**：四道闸防自证（题库哈希/判分器校准/输入隔离/预注册），修复前 self_top1 仅 3.3%，暴露出「自己的测试全绿但链路是断的」；
- **Anima**：architecture.md 诚实声明「quality has not been benchmarked」。
- **判断**：新架构把「独立验证」作为一等公民写入设计，不允许「自测通过」单独作为能力证明。

### 交叉 6（冲突）：Dreaming 的后台综合 ↔ DSH 的读时组合

- **冲突本质**：consolidate-at-rest（写入期后台把记忆综合成新事实）与 compose-at-read（读时组合，不预生成派生事实）是相反的工程路线。
- **裁决**：DSH 维持读时组合（ADR-004，铁律「User Model 永远是读时组合的视图」）。后台综合仅作为 V2 的有条件机制（触发条件：库规模 + 真实使用时态错误率达标），且必须借鉴 Anima 的 worker lease + review + 显式 retry 故障恢复范式。**不借鉴** Dreaming 的「自动人格推断」「usageBoost 前台后台二分」。

### 交叉 7（2026-11 新证据）：Raw-history RAG 的竞争力挑战「复杂 Agent Memory」路线

- **新证据（哥哥提供，2026-10 以来多项独立研究相近结论）**：直接检索原始对话历史（Raw-history RAG）在不少长期记忆基准上**超过**复杂 Agent Memory；记忆提炼/压缩/重写/结构化可能丢失原始关键信息；复杂记忆系统增加构建/维护成本却不一定换来更高准确率。
- **外部独立评审 立场（哥哥转述）**：支持把 RAG 作为 DSH 的主要检索基础，但不支持把 DSH 简化为纯 RAG。
- **与我方 LoCoMo 实测的关系（关键辨析）**：LoCoMo R@5 13.4% 是「DSH 结构化记忆 + 手写词法打分」的表现，**不是 Raw-history RAG 的上限**。这组新研究说明：DSH 在「结构化记忆 + 六因子词法打分」上投入的巨大复杂度（台账 #42），可能不如直接把原始历史 embed 起来检索。
- **判断改变（重要自我修正）**：检索召回主力应从「结构化记忆的词法召回」**转向「Raw-history RAG（原始历史 + embedding 检索）」**；结构化记忆**不再承担检索召回主力**，其唯一不可替代的职责是「维护事实的当前状态（时态正确性 + 失效管理 + 矛盾显式化）」——这是 RAG 做不到的。

## 1.3 收敛出的三条核心判断

五部分资料收敛为三条判断，这三条就是新架构的全部骨架，其余都是它们的展开：

1. **职责分层**（回应 #46/#47）：证据层（原始历史，按需检索）、事实层（结构化事实，带时态治理）、组装层（Context Assembly）三者分离，各司其职，不互相替代。
2. **事实时态治理**（回应 #57/#48/#49）：为事实层引入时态类型（temporal_kind）与失效二态（invalidation），让「这条现在还是真的吗」成为可回答、可校验的问题。
3. **检索交给 Raw-history RAG，结构化记忆专注状态维护**（回应 #42/#32/#17/#50/#51 + 交叉 7 新证据）：检索召回主力从「手写词法打分」转向「原始历史 + embedding 检索」；结构化记忆瘦身为「状态维护层」，只做 RAG 做不到的事——维护事实的当前状态（时态正确性、失效管理、矛盾显式化）。

# 第二部分 · RAG / 结构化记忆 / Dreaming 职责协同

## 2.1 三者各自解决的问题（不预设替代关系，也不预设必须全要）

| 职责 | 解决的问题 | 在 DSH 语境下的形态 |
|---|---|---|
| RAG（原始证据检索） | 从原始对话/历史按需找回相关证据，回答「当时发生了什么、原话是什么」 | 证据层；LoCoMo A-R 就是它的实测 |
| Structured Memory（结构化记忆） | 维护经提取、验证的长期事实/状态/领域知识及其历史变化，回答「他现在是谁/在干嘛/喜欢什么」 | 事实层；现有 memories 表 + 待补的时态治理 |
| Dreaming / Consolidation（后台整理） | 跨时间综合已有信息，识别值得综合/更新/纠正/废弃的派生记忆 | 组装层之上的可选后台；留 V2 有条件 |
| Context Assembly（上下文组装） | 按当前任务组织原始证据 + 结构化记忆 + 必要上下文给模型 | 组装层；对应现有 read_for_context / 注入通道 |

关键立场：**四者不是竞品，是流水线的四段**。DSH 当前的病（#46）恰恰是四段职责在一处实现、互相污染。

## 2.2 核心问题逐条回答（约束二要求的）

- **RAG 能否覆盖 DSH 大部分长期记忆需求？** **检索（召回）层面，能；「事实状态维护」层面，不能。** 2026.10 多项研究证明 Raw-history RAG 在不少基准上超过复杂 Agent Memory，原始历史 + 现代检索是召回首选（我方 LoCoMo R@5 13.4% 是「DSH 手写词法打分」的表现，不是 Raw-history RAG 的上限）。但 RAG 只能找回「原文」，无法维护「事实的最新状态」——用户搬家后，RAG 会同时捞到旧地址和新地址，却不知道哪个是当前的（台账 #57/#48/#49）。所以：**检索靠 RAG，状态维护靠结构化记忆，二者分工，不是 RAG 替代结构化记忆。**
- **哪些信息适合直接原始历史检索？** 一次性事件细节、长篇上下文、用户原话、跨会话的具体讨论——这些没有「可更新的状态」，按需检索比预先结构化更合适。
- **哪些信息必须结构化保存，不能每次依赖原始记录重新推断？** 有状态、会过期、会被更新的信息：身份、当前备考阶段、住址、偏好、领域约定。这些必须结构化 + 带时态，否则每次都要重读历史重新推断，且无法回答「现在还是真的吗」。
- **Dreaming 是否有检索不可替代的价值？** 有，但价值在「时态正确性」和「跨时间综合」，不在「替代检索」。官方数据显示时态正确性提升最陡，但无第三方复现；且 DSH 是读时组合路线，后台综合与铁律「读时组合视图」有张力。结论：价值存在，但**当前证据不足以让它进 V1**。
- **哪些整理工作可由确定性程序完成，哪些才需要 LLM？** 过期判定、失效二态转换、同槽位冲突检测、supersede 链维护——确定性程序；语义等价判断、跨 key 矛盾仲裁、派生摘要综合——才需要 LLM（且应保守、可审计）。
- **结构化记忆如何与原始证据一致？** 每条结构化事实带 source_message_id（已有）+ 建议补 source_quote（句级引用，Anima 做法）+ 失效时保留 superseded_by 链，使任何事实都能回溯到原始证据。
- **新证据与已有结构化记忆冲突时如何判断？** 先确定性判据（同槽位 + 时态 + 极性），再语义仲裁（LLM，保守），永不自动取代高置信显式事实（铁律 ADR-023）。台账 #49 证明当前 supersede 方向反了，需重做冲突判据。
- **Dreaming 产生的派生记忆是否可能降低原始信息可检索性或准确性？** 会。派生摘要若替代原始证据，会丢细节；若与原始冲突，会污染。Anima 的「派生描述只帮助检索、永不替代原始证据」是正确原则。因此 DSH 若做 Consolidation，派生记忆必须是「检索辅助」，不能成为事实层的权威来源。
- **三者协同是否真正优于单独 Raw-history RAG？** 是，但理由要分清：Raw-history RAG 在「召回原文」上已很强（交叉 7），它缺的不是召回、是「事实状态维护」——台账 #47/#48/#57 证明「只靠原文检索」无法维护时态正确性、无法防止运行时状态污染。所以协同不是「RAG 召回不够、用结构化补」，而是「RAG 管召回，结构化记忆管状态维护，二者正交、缺一不可」。**

## 2.3 四候选架构对比（12 维度）

候选：A Raw-history RAG；B Structured Memory；C Hybrid Memory + RAG；D Hybrid + Controlled Consolidation。

评价用「强 / 中 / 弱」，附一句理由（DSH 语境，非通用）。

| 维度 | A Raw-history RAG | B Structured Memory | C Hybrid | D Hybrid+Consolidation |
|---|---|---|---|---|
| 信息完整性 | 强（全量历史） | 弱（丢原始上下文） | 强（证据+事实） | 强（+派生摘要） |
| 原始证据保留 | 强 | 弱 | 强 | 强 |
| 事实更新能力 | 弱（无状态，每次重推断） | 中（依赖治理质量） | 强（事实层+证据层可溯） | 强 |
| 时间状态正确性 | 弱（过时信息照捞） | 中（需补时态字段） | 强（引入 temporal_kind/invalidation） | 强 |
| 实体归属准确性 | 弱（无主体字段） | 强（subject_type） | 强 | 强 |
| 检索召回与证据覆盖 | 强（2026.10 研究证 Raw-history RAG 召回强） | 中（依赖写入质量） | 强（证据+事实互补） | 强 |
| 上下文利用效果 | 弱（检索弱则上下文弱） | 强（精确事实直接注入） | 强 | 强 |
| 持续更新后稳定性 | 中（历史只增，但检索不稳） | 中（依赖写入治理） | 强（事实层稳定，证据层可回退） | 中（派生可能污染） |
| 模型调用成本 | 高（每次检索+重读+重推断） | 中（写入提取成本） | 中 | 高（+后台整理） |
| 存储及索引维护成本 | 中（全存但无索引维护） | 低（只存事实） | 中 | 高 |
| 工程复杂度 | 低 | 中 | 高（两套检索+一致性） | 最高 |
| 故障恢复能力 | 强（无状态易恢复） | 中（有状态需维护） | 中强 | 中（worker 需 lease 机制） |

### 2.4 架构选择与理由

**选择 C（Hybrid Memory + RAG）作为目标架构，D（Consolidation）作为 V2 的有条件扩展，A 是现状起点、B 是已否决的退化方向。**

理由（每条对应约束二要求的决策说明）：

1. **原先设计是什么**：v0.2.0 的 DSH 是「结构化记忆为主 + 词法检索」——实际上接近 B，但检索靠手写打分因子（台账 #42 称其「高复杂度低验证」）。
2. **新资料提供了什么证据**：2026.10 多项研究（Raw-history RAG 召回超复杂记忆，交叉 7）、台账 57 条（B 的污染/过期/失时态反例）、Anima（时态治理机制）、Dreaming（D 的成本与张力）。
3. **证据如何影响判断**：A 召回强但「无事实状态维护」（用户搬家后不知哪个地址当前）；B 丢证据 + 治理失效；D 过早（无第三方复现 + 与读时组合铁律张力 + 成本高）。只有 C 同时满足「保真（证据层 RAG 召回）+ 保时态（事实层状态维护）」。**
4. **为什么选 C**：它把「找回原文」和「维护现状」两个不同职责分开，正好治愈 #46 职责混层；且不新增后台负担。
5. **为什么不选其他**：A（纯 Raw-history RAG）召回强但无「事实状态维护」——用户搬家后不知哪个地址当前（台账 #57）；B 丢原始证据、无法诚实回溯；D 的证据不足且成本高，留 V2 有条件触发。**
6. **仍存不确定性**：Hybrid 的两套检索如何保持一致性、证据层在 DSH（不存全量历史的铁律）下如何落地的范围边界，仍需在实现中定（见第六部分）。

# 第三部分 · 实施边界（五类范围表）

## 3.1 特别审视项逐一定位（约束三列出的 9 项技术）

每一项都回答：它解决什么已知问题？没有它是否仍满足需求？是否已有更简单替代？引入成本？如何证明收益？何时引入/延期/放弃？

| 技术 | 定位 | 理由 |
|---|---|---|
| 向量检索（embedding 索引原始历史，Raw-history RAG 组件） | **V1 必需（检索基础）** | 2026.10 研究证明 Raw-history RAG 是召回首选，对原始历史做 embedding 索引是其必要组件；旧的「库 < 500 条词法够」约束被交叉 7 证据推翻。专用向量数据库（独立于 SQLite 的向量表）仍视规模待定 |
| 知识图谱 | **暂不引入** | 实体归属已由 subject_type/domain_key 表达；#46 的职责混层不是图能解决；图会引入新的 schema 维护与一致性成本 |
| 复杂 Agentic Memory | **暂不引入** | DSH 是记忆插件，不是 agent 框架；Agentic Memory（自主规划写什么）与「宁漏记不误标」铁律直接冲突 |
| 多层自动摘要 | **暂不引入** | 与「读时组合视图」铁律冲突；派生摘要替代原始证据会丢细节（Anima 原则：派生只助检索、永不替代证据） |
| 高频后台 Dreaming | **暂不引入** | 读时组合路线 + 无第三方复现 + 模型成本；留 V2 有条件（见 3.4） |
| 自动人格/心理特征推断 | **暂不引入** | Dreaming 报告明确「自动人格推断不值得」；台账 #55「称呼 preference 被赋予过高 importance」正是自动推断的反例 |
| 过于复杂的记忆评分体系（手写词法打分） | **暂不引入（且用 RAG 取代）** | 台账 #42 证六乘数因子 + 三阶段管线只换来 13.4% 召回；交叉 7 进一步证明应直接转向 Raw-history RAG，而不是继续修手写因子 |
| 多种重复记忆分类 | **暂不引入** | 现 type/subtype 已覆盖；再引入 Entity/Fact/Episode 是重复维度（台账 #47 关联项，判断为不引入） |
| 不必要的模型调用/后台任务 | **暂不引入** | 写入意图准入门 + 无盲目付费重试（Anima 范式），从入口减少无谓调用 |

## 3.2 V1 必需（核心需求，缺了就无法可靠运行）

每项格式：问题（台账编号）→ 机制 → 验收条件。

### V1-1 事实时态治理（temporal_kind + invalidation + freshness）
- **问题**：#57（缺「内容现在是否仍为真」的持续校验）、#48（过期记忆标长期有效）、#49（supersede 方向反）、#27（tick 无自动调度）、#10（个位数数值被关键词过滤致误判 touch）。
- **机制**：为事实层引入三个正交字段——temporal_kind（current/historical/event/uncertain，默认 current 兼容旧库）、invalidation（None/corrected/superseded）、freshness（valid_until + last_verified，任何可失效类型都能设有效期，修 #48 的「仅 state 可过期」类型设计错误）。corrected 的记忆在任何视图永不召回；superseded 的记忆在 as-of 查询可召回（Anima 机制）。
- **验收**：新增 B 层场景「纠正后的错误旧值绝不复活」「as-of 查询返回当时事实」「事件型事实按 event_date 检索」；生产库中「备考 2026 初试」等天然过期项在 valid_until 后不再注入；supersede 的触发方向与用户真实意图一致（措辞修正不再触发 supersede）。

### V1-2 职责分层（证据层 / 事实层 / 组装层）
- **问题**：#46（语义判断、投递逻辑、治理职责混层）、#47（长期库被运行时状态污染、task scope 零使用）、#40（宿主耦合过深）、#14（全局 interaction 记忆无注入通道）。
- **机制**：把现在的单引擎拆成三段职责——证据层（原始历史，按需检索，可选）、事实层（结构化事实 + 时态治理，即现在的 memories 表增强）、组装层（Context Assembly，按任务组织注入）。写入意图准入门（长期事实 vs 任务状态 vs 领域知识 vs 运行时配置）决定一条信息进哪一层，而不是让模型靠 type/scope 猜。
- **验收**：窗口角色、协作协议、任务状态不再进入事实层；task scope 有真实写入（不再为零）；每个写入路径有明确的目标层，无「存储成功但无通道消费」的孤儿（#14）。

### V1-3 检索主力转向 Raw-history RAG（原始历史 + embedding 索引）
- **问题**：#42（高复杂度低验证）、#32（relevance 广播）、#17（updated_at 截断）、#50（domain_key 漂移）、#51（垃圾关键词）、#38（缺规模基准）+ 交叉 7（手写词法打分不如 Raw-history RAG）。
- **机制**：以 Raw-history RAG 为检索召回主力——对原始对话历史建 embedding 索引，查询时按语义召回证据；结构化记忆的词法检索**退居辅助**（稳定块 S1 注入 + memory_search 显式查询仍走事实层）；domain_key 建注册表 + alias 归一（修 #50）；keywords 保留标识符字符（修 #51，作事实层兜底而非主力）。
- **验收**：Raw-history RAG 的召回（LoCoMo/LongMemEval A-R）显著高于当前词法 13.4%，cat3 时间类相对提升；结构化记忆不再承担召回主力但仍正确注入稳定块；domain_key 无漂移；500–5000 条规模基准跑通。

### V1-4 冲突与 supersede 判据重做（确定性优先，语义仲裁保守）
- **问题**：#49（真变更未 supersede、措辞修正反而 supersede）、#11（同槽位多值同时 active）、#10（个位数数值被过滤）、#33（兜底抽取把否定偏好记成肯定）。
- **机制**：先确定性判据（同槽位 = 同 subject_type+subject_name+属性 key；时态类型；极性词表含否定/废弃/沿用），再语义仲裁（LLM，保守，可审计），永不自动取代高置信显式事实（铁律 ADR-023）。修正抽取器的否定极性判定（#33）。
- **验收**：B 层新增「措辞修正不 supersede」「真变更才 supersede」「否定偏好不记成肯定」「同槽位互斥」四场景；生产反例 4-4→2-4（措辞修正误 supersede）不再复现。

### V1-5 独立验证体系落地（基准 + 四道闸 + 规模基准）
- **问题**：#39（验证靶子错位）、#43（文档替代验证）、#31（测试覆盖作者预设路径）、#38（缺规模基准）、#23（契约自检失败永久 unavailable）。
- **机制**：外部评价体系 v1 已建（LongMemEval + LoCoMo + 四道闸 + 防自证），补齐 LongMemEval 实测 + 500–5000 条规模基准 + 负向断言；引擎契约自检失败后支持重试（修 #23）。
- **验收**：LoCoMo + LongMemEval 均跑通且状态 UNVERIFIED（可交第三方）；「自测全绿」不再被单独当作能力证明。

### V1-6 可观测性修复（送达 vs 渲染分离）
- **问题**：#52（聚合注入指标与真实送达不一致）、#54（always 零观测）、#53（历史计数器不能倒推历史）、#19（preview 与真实 add 决策不一致）、#24（读路径污染 use_count）、#36（purge 不保留 tombstone）。
- **机制**：事件分账（candidate/generated/rendered/delivered/visible/used 分开记账，只有进模型消息的计 delivered）；稳定块（always）必须有送达日志 + 配额 + 一键关闭；聚合指标带 schema/version/started_at/coverage（修 #53）；读路径只读不写；purge 保留独立 tombstone。
- **验收**：「注入 0 / 使用 31」这类假象不再出现；always 稳定块有逐条送达观测；「未观测到」与「未发生」在报告里可区分。

### V1-7 数据一致性与事务收口
- **问题**：#12（purge 非事务）、#13/#35（merge 绕过 validate/value_gate）、#22（update 绕过生命周期）、#37（verify_invariants 未按 user_id 分组）、#30（秒级时间戳碰撞）、#10（个位数数值被过滤）。
- **机制**：purge 单事务（软删 + 物理删 + tombstone 原子）；merge/update 走统一 validate + 生命周期规则；verify_invariants 按 user_id 分组；时间比较用高精度。
- **验收**：purge 中断不破坏审计链；merge 无法写入空内容/非法 active；update 无法绕过有效期。

## 3.3 V1 可选（有收益但不影响核心成立）

# 第四部分 · 最终架构设计

## 4.1 三层架构总览

    组装层 Context Assembly   按当前任务组织：稳定块(S1) + 相关记忆(S2) + 任务上下文(T) + 证据片段
             ▲ 只读组合（铁律：User Model 是读时组合的视图，不建双写副本）
    事实层 Structured Memory  memories 表 + 时态治理（temporal_kind / invalidation / freshness）
             ▲ source_message_id + source_quote 回溯
    证据层 Evidence           宿主会话历史（复用，不重复存储）+ 选择性 source 快照（保底回溯）

三层各自有明确的「写入口」和「消费方」，不再互相污染（治 #46）：

| 层 | 写入口 | 消费方 | 不做什么 |
|---|---|---|---|
| 证据层 | 宿主历史（外部）+ 事实写入时的 source 快照 | 组装层按需回捞原文、memory_explain 回溯 | **不自建全量 evidence 表**（铁律：不存全量聊天记录） |
| 事实层 | memory_remember / supersede / 抽取通道（过写入意图准入门） | 组装层、memory_search、memory_explain | 不存运行时状态/任务配置（归宿主或 task scope） |
| 组装层 | 无（只读，由 read_for_context 组合） | 模型上下文 | 不写库、不污染 use_count（修 #24） |

## 4.2 事实层：时态治理字段设计（V1-1 核心）

为 memories 表新增（进 metadata 或独立列，兼容旧库默认值）：

- **temporal_kind**：current（默认，兼容旧数据）/ historical / event / uncertain
- **invalidation**：None / corrected / superseded（语义失效类型，与 status 正交）
- **event_date**：事件发生日（仅 event 类使用，与 valid_from/valid_until 的「有效期」分离）
- **last_verified**：最后核验时间（freshness 的一环）
- **valid_until**：已有字段，但**扩展语义**——任何可失效类型（profile 阶段身份、domain 版本事实、state 备考阶段）都能设，修 #48 的「仅 state 可过期」类型设计错误。

语义规则（对应 Anima 三时钟分离）：

- occurrence（event_date）≠ observation（created_at/source 时间）≠ validity（valid_from/valid_until）。三者分离，不互相冒充。
- invalidation = corrected：被纠正的错误，任何视图（含 as-of）永不召回；
- invalidation = superseded：被更新取代，as-of 查询可召回（曾经为真）；
- uncertain（temporal_kind）：推断所得、低置信，默认降权、不注入稳定块、可被显式事实覆盖。

查询语义扩展：memory_search / read_for_context 增加「as-of」能力（可选），回答「2026 年 5 月时地址是什么」这类问题。

## 4.3 检索路线设计（V1-3 核心）

检索主力 = Raw-history RAG（原始历史 embedding 索引 + 语义召回），结构化记忆的词法检索退居辅助：

    证据层检索（主力）：原始对话历史 → embedding 索引 → 语义召回证据片段 → 注入组装层
    事实层检索（辅助）：稳定块(S1) 直接注入 + memory_search 显式查询 + 相关记忆(S2) 兜底
      → 事实层只做结构化过滤（type/subject/scope/domain/status，corrected 永不进候选）
      → 不再维护六因子词法打分（#42 的复杂管线被 RAG 取代）

- embedding 索引原始历史 → V1 必需（Raw-history RAG 组件，交叉 7）；
- FTS5 / bigram 倒排 → 待实验（作 embedding 的廉价兜底，A/B 见 3.6）；
- domain_key → 注册表 + alias 归一（修 #50）。

## 4.4 组装层设计（V1-6 核心）

- **事件分账**：candidate（进入候选）/ generated（生成）/ rendered（渲染进稳定块或上下文块）/ delivered（进入模型消息）/ visible（模型可见）/ used（模型实际引用）六态分开记账；只有 delivered 计入「送达」，只有 used 计入「使用」。
- **稳定块（always）受控**：独立授权 + 配额 + 逐条送达日志 + 一键关闭（修 #54/#34/#15）。
- **task scope 成为真实路径**：运行时/任务状态走 task scope 或宿主，不进事实层（修 #47）。

## 4.5 与 v0.2.0 的延续关系

- v0.2.0 的「架构收口」（SSOT / explicit 默认 False / 删 forget hard / 抽取四计数 / 死链闭合 / fail-closed 三态）**全部保留，不推翻**；
- v3 是在其之上的**职责跃迁**：v0.2.0 回答「能不能跑对」，v3 回答「能不能持续跑对（时态/新鲜度/独立验证）」；
- 命名沿用公开 v0.x.y 一套，本设计书对应下一版本的架构方向，具体版本号等哥哥指令。

## 5.2 关键决策追踪（约束一第 6 点，每个决策六问）

### 决策 1：选择 Hybrid（C）而非 Raw-history RAG / 纯结构化 / 过早 Consolidation
- 原设计：v0.2.0 是「结构化记忆 + 词法检索」，接近 B；
- 新证据：2026.10 多项研究（Raw-history RAG 召回超复杂记忆，交叉 7）、台账 #46/#47/#48/#57（B 的污染/过期/失时态）、Dreaming 无复现 + 成本（D 过早）；
- 判断如何改变：A 召回强但无事实状态维护、B 丢证据且治理失效，二者单独都不够；
- 为什么选 C：证据层保真 + 事实层保时态，同时治愈 #46；
- 为什么不选其他：见 2.4 第 5 条；
- 剩余不确定性：证据层在 DSH「不存全量历史」铁律下的落地范围（见 6.1）。

### 决策 2：引入时态治理（temporal_kind + invalidation）
- 原设计：DSH 只有 status=superseded + valid_until（且仅 state 可设有效期）；
- 新证据：台账 #57/#48/#49 生产反例 + Anima 的 temporal 模块与测试 + Dreaming「随时间正确提升最陡」；
- 判断如何改变：时态从「附属字段」升格为「事实正确性的组成部分」；
- 为什么选：生产数据背书，机制成熟（Anima 有测试）；
- 为什么不选其他（如只加 last_verified 或只加 freshness）：单加时间戳不能区分「纠正」与「更新」，不能回答 as-of 查询；
- 剩余不确定性：中文语境下 temporal_kind 的自动分类准确率（可能需人工/显式标注，见 6.2）。

### 决策 3：职责分层（证据/事实/组装三层）
- 原设计：单引擎混层；
- 新证据：#46 宏观根因 + #47 污染反例 + Dreaming 的 consolidate vs compose 对比；
- 判断如何改变：分层应在写入口做，不是靠后台整理补救；
- 为什么选：三层职责单一，写入口各自明确；
- 为什么不选「继续单引擎 + 打补丁」：#46 明说局部补丁绕回新缺陷；
- 剩余不确定性：证据层复用宿主历史的耦合风险（#40）如何隔离（见 6.1）。

### 决策 4：检索主力转向 Raw-history RAG
- 原设计：六乘数因子 + 三阶段管线（手写词法打分）；
- 新证据：#42「高复杂度低验证」+ LoCoMo 实测 13.4% + 交叉 7（2026.10 研究证 Raw-history RAG 超复杂记忆）；
- 判断如何改变：不是「删因子、上基准」，而是「放弃手写词法打分，转向 Raw-history RAG」；
- 为什么选：手写词法打分复杂度高却只换来 13.4%，Raw-history RAG 是经过外部研究验证的召回首选；
- 为什么不选「继续修词法因子」：交叉 7 证明方向错了；
- 剩余不确定性：embedding 索引原始历史在 DSH「不存全量历史」铁律下的落地范围（见 6.3 决策 1）。

### 决策 5：Consolidation 留 V2 有条件，不进 V1
- 原设计：DSH 是读时组合，无后台综合；
- 新证据：Dreaming 官方三维 eval 无第三方复现 + consolidate-at-rest 与读时组合铁律的张力 + 模型成本；
- 判断如何改变：价值存在但证据不足，且与铁律有张力；
- 为什么选：维持读时组合（ADR-004 铁律）；
- 为什么不选「现在引入」：无复现、成本高、与铁律冲突；
- 剩余不确定性：触发条件（库规模 + 时态错误率）的具体阈值需真机数据定。

# 第六部分 · 未解决 / 待验证假设 / 需用户决策

## 6.1 未解决的问题（如实登记，不擅自标记为已解决）

1. **宿主耦合隔离（台账 #40）**：证据层若做 Raw-history RAG，需索引宿主历史，引入「宿主重构 → 记忆能力静默失效」的风险。缓解手段是「事实层 source 快照保底 + 引擎契约自检 + 启动 fail-closed」，但**根本隔离**依赖是否抽成 MCP Server（见 6.3 决策 2）。当前未决。
2. **Hybrid 两套检索的一致性**：证据层检索（回捞原文）与事实层检索（结构化召回）如何保证「同一查询、互补结果、不互相打架」，尚未设计到实现级。
3. **temporal_kind 的中文自动分类**：current/historical/event/uncertain 四态在中文短句下能否被模型稳定区分，未验证（可能需显式标注 + 人工校准，见 6.2 假设 1）。

## 6.3 需用户决策的事项

1. **证据层形态（Raw-history RAG 落地范围）**：是否对原始对话历史建 embedding 索引、作为检索主力？这需要重新权衡「不存全量聊天记录」铁律——若引入 Raw-history RAG，需明确「存什么范围的原始历史、embedding 索引的保留期、与宿主历史的耦合边界」（#40）。可选三档：a) 只索引「事实的 source 快照」（最小）b) 索引「近期 N 天原始历史」（折中）c) 索引「全部原始历史」（最强但最重）。
2. **MCP Server 路线（台账 #41）**：是否把 Memory Engine 抽成独立 MCP Server（而非继续把 DSH 接线当核心产品）？这是路线级决策，决定后续所有开发与 #40 的根本解法。
3. **V1 七项的实施顺序**：建议 V1-1 时态治理 → V1-2 职责分层 → V1-4 冲突判据 → V1-3 检索收敛 → V1-6 可观测性 → V1-7 数据一致性 → V1-5 独立验证；是否按此排序、是否分阶段交付，请拍板。
4. **基准起点**：是否立即跑 LongMemEval 全量 + LoCoMo 复测，作为 Raw-history RAG 的召回基线（V1-3 验收依赖此基线；同时保留当前词法 13.4% 作对比基准）？
