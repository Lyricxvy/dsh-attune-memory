# 外部评价体系 v1（2026-11-19）

> 目标只有一个：**让"自己出题、自己测试、自己宣布通过"这件事在结构上做不到**，
> 而不是"再写一套更严的自测"。
>
> 本文件是规则，不是成绩。成绩在 `.ext-runs/<bench>-<时间>/` 里，且默认状态是
> `UNVERIFIED`——没有第三方签字，它就不是结论。

---

## 1. 为什么自测不算证据

现有 `engine/eval/run_eval.py` 的 24 个场景、引擎单测、插件测试，都是我们自己写的：
题是我们挑的，期望是我们定的，判据是我们解释的，报告是我们发的。这类测试能防回归，
**不能证明能力**——它只证明"系统符合我们自己的想象"。

三个环节各自都能被自己解释，所以要把它们分开交给三个不同的来源：

| 环节 | 谁来做 | 我们能不能改 |
|---|---|---|
| 出题 | 公开数据集作者（LongMemEval / LoCoMo） | 不能改题，只能选子集，子集规则写进 run.json |
| 判分 | `score.py`：确定性脚本，无 LLM judge | 能改，但改判分必须 bump 版本并重跑全部历史 |
| 签字 | 独立第三方（人，或另一个模型），按 §8 清单核验 | 不能，我们只能提交 UNVERIFIED |

**我们能做的上限**：把 `UNVERIFIED` 的报告和原始产物交出去。

---

## 2. 两个基准，各自的边界

| | LongMemEval | LoCoMo |
|---|---|---|
| 出处 | Wu et al., ICLR 2025（arXiv 2410.10813） | Maharana et al., ACL 2024（arXiv 2402.17753） |
| 许可 | MIT | CC BY-NC 4.0（仅限非商业研究使用） |
| 规模 | 500 题 / 6 类 | 10 段多年对话 / 1986 个 QA / 5 类 |
| 标准答案 | `answer_session_ids`（session 级） | `evidence` 里的 `dia_id`（轮次级） |
| 模式 | **A-R**：只测检索 | **A-R**：只测证据召回 |
| 测什么 | 长程检索、知识更新后能否捞到新 session、时间/多会话推理 | 证据轮次召回、时间与多跳 |
| 不测什么 | 写入治理（supersede / 遗忘 / scope / 注入预算） | 同上，且不测答案生成质量 |

**这两层不能互相解释**：

- A 层分数高，不代表写入治理对（旧值复活、串线、误删它测不到）；
- 自己的 B 层 case 全绿，不代表能力已被独立验证（题是我们出的）；
- 因此对外只能说"A-R 上召回率是多少"，不能说"记忆系统合格"。

## 3. 指标（跑前冻结，不许跑完再定义）

- `Recall@k` = |top-k 去重单元 ∩ 标准答案单元| / |标准答案单元|
- `Hit@k` = top-k 里至少命中一个标准答案单元
- `Random Recall@k` = k / n（无放回抽样的期望值，n = 该 case 的候选单元数）
  —— 这条是"读数是否有意义"的标尺：分数贴着随机线，说明检索没在工作。
- `Ingest coverage` = 实际入库块数 / 应入库块数（产品准入会丢弃一部分，如实报告）

**K 只取 5 / 10 / 20**。原因：引擎单次检索硬上限 `const.K_HARD_MAX = 20`
（`engine/attune_memory/const.py:77`），更大的 K 会被静默截断——报 R@50 等于自欺。
排名只算一次，所有 K 都从同一份排名里截断，不允许为不同 K 重跑排序。

## 4. 四道闸

### 闸一：题库哈希
`registry.json` 记死每个数据集的 SHA-256、字节数、许可、上游地址与镜像地址。
`fetch.py` 下载后强制校验，对不上直接退出。换一份题库在物理上不会悄悄发生。

### 闸二：判分器校准 + 变异
`test_scorer.py` 共 15 条，其中最关键的是**变异测试**：

- 随机排序器 → 必须得到 ≈ k/n（5%），偏差超 2 个百分点就红；
- 完美排序器 → 必须 1.0；
- 反向排序器（把正确答案压到最后）→ 必须 0.0。

先证明"判分器会红"，才有资格相信它的绿。

### 闸三：输入隔离
- `run.py` 只负责灌数据、取排名，**不读标准答案**，不 import 判分逻辑；
- `score.py` 只读 `predictions.jsonl` + 数据集文件，**不 import 引擎**；
- 两者之间唯一的接口是文件。谁想作弊，就得改一个"看起来毫无必要"的文件。

### 闸四：预注册 + 默认未审计
- 跑之前先把 case 列表、seed、K、数据集哈希、引擎代码指纹写进 `run.json`；
- 报告生成时状态一律是 `UNVERIFIED`；
- 只有 §8 的审计清单被第三方逐条填完并签字，才允许改成 `VERIFIED`。

### 闸五：控制实验（不需要标准答案的冒烟测试）
把库内每条记忆的**原文**当作查询去检索它自己（`control.py`）。这不涉及任何标准答案，
所以它连"题目出得对不对"都不用信任，就能回答一个问题：**检索链路是不是通的**。
顶部只报两个数 `self_top1 / self_top5`。

- 期望：`self_top1` 接近 100%（原文是这条记忆最完整的描述）；
- 危险信号：低于 50%。这时**不要**去看分数、调参数，先查链路。
  首轮 LoCoMo 的 0.5% 就是被这个实验定位成一个打分 bug 的（见《外部基准-首轮发现.md》）。

任何一次对外报告都必须附上这两个数。它便宜（200 条记忆、30 次抽检、几十秒），
但它是唯一能在"题太难"和"代码坏了"之间划清界限的东西。

## 5. 怎么跑

```bash
cd engine

# 1) 取数据（首次）
python -m eval.external.fetch --name locomo10 --dest ../.ext-dl/locomo10.json
python -m eval.external.fetch --name longmemeval_s --dest ../.ext-dl/longmemeval_s

# 2) 先证明判分器可信
python -m unittest eval.external.test_scorer -v

# 2.5) 控制实验：不碰标准答案，先证明检索链路是通的（闸五）
python -m eval.external.control --bench locomo --units 200 --probes 30

# 3) 跑（只产生产物，不判分）
python -m eval.external.run --bench locomo --data ../.ext-dl/locomo10.json \
    --out ../.ext-runs/locomo-$(date +%Y%m%d)
python -m eval.external.run --bench longmemeval --data ../.ext-dl/longmemeval_s \
    --n 40 --haystack 20 --out ../.ext-runs/lme-$(date +%Y%m%d)

# 4) 判分 + 出报告（参数必须与 run.json 一致）
python -m eval.external.report --run-dir ../.ext-runs/locomo-20261119 \
    --bench locomo --data ../.ext-dl/locomo10.json
```

## 6. 产物长什么样

```
.ext-runs/<bench>-<时间>/
  run.json            预注册：数据集哈希、case 列表、seed、K、引擎代码指纹、耗时
  ingest.json         入库统计（应入库 / 实际入库 / 被准入丢弃）
  ledgers/<shard>.jsonl   memory_id ↔ 原始语料单元（session / dia_id）
  predictions.jsonl   每 case 一行：ranked 单元顺序（**不含分数，不含标准答案**）
  report.json / report.md  判分结果（默认 UNVERIFIED）
```

第三方拿到 `predictions.jsonl` + 数据集文件，可以**绕过我们的 score.py 重写判分**
再算一遍。这就是"可复算"的含义。

## 7. 已知偏差与限制（必须写进任何对外报告）

1. **LongMemEval 用了 haystack 子集**（`--haystack N`）：证据 session 必留，其余按
   哈希序补足。不是全量 500 session，分数**不能**跟论文/榜单横向比较。
2. **LoCoMo 数据来自镜像仓**：本环境不能直连 GitHub。sha256 与镜像声明一致，
   但与上游原件的一致性未由我们独立验证。
3. **单次检索上限 20、候选集上限 200**（`MAX_CANDIDATES`）：语料超过 200 块时，
   候选截断本身就会掉分，这部分掉分是产品行为，不是适配器 bug。
4. **写入期是线性查重**：同一 slot（type/subtype/subject）里所有记忆都会参与
   `find_similar`，语料同质化时写入退化为 O(n²)。这是本次接入暴露的真实性能问题，
   与检索质量无关，但限制了可跑的语料规模。
5. **没有 LLM judge**：只算检索，不算"答得对不对"。这是有意的——judge 会引入
   "自己判自己"的第二个黑箱。
6. **LoCoMo 第 5 类（对抗题）没有证据轮次**，不计入召回，单独计数。

## 8. 第三方审计清单（签字前必须逐条回答）

1. `run.json` 里的 `data_sha256` 和你自己下载的文件一致吗？
2. `case_ids` 的选择规则（`--n` / `--haystack` / `--seed`）你能用同样参数复现吗？
3. `predictions.jsonl` 里每行的 `ranked` 是否只含单元 id、不含任何标准答案？
4. `score.py` 是否 import 了引擎？（不允许）
5. `run.py` 是否读取了 `gold`？（不允许）
6. `test_scorer.py` 的变异测试是否真的会让随机排序器掉到 ≈ k/n？
7. 报告里的 K 是否 ≤ 20？更大的 K 是否被明确标注为"被引擎截断"？
8. `ingest.json` 的入库损失是否在报告里体现，而不是被忽略？
9. 失败样例是否被列出（不是只报平均分）？
10. 报告状态是否仍然是 `UNVERIFIED`，直到你签完这一条？

## 9. 发版门槛（v1 只定"不许更差"，不定"必须达到多少"）

- 硬门槛：任何一次发布，A-R 的两个基准都必须有可比的同参跑；
- 硬门槛：`ingest coverage` 出现明显下降时必须解释（是准入变严还是写入坏了）；
- 量化门槛：**首次完整基线冻结之后**，核心指标下降超过 0.03 必须阻止发布，
  除非在报告里明确写出原因并得到审计人确认；
- 禁止：拿 A 层分数宣传"记忆系统通过验收"。

## 10. 与 B 层的关系

外部基准回答"能不能找到"，B 层（`run_eval.py` 那 24 个场景）回答"守不守规矩"。
B 层的题是我们自己出的，所以：

- B 层结果只能作为**内部回归**，不能作为对外证据；
- B 层新增案例必须能追溯到"真实发生过的失败"，并且有脱敏记录；
- A 层不会因为 B 层全绿而变绿，反之亦然。

**结论：本项目对外可提交的最高形态是"外部题库 + 确定性判分 + UNVERIFIED 报告 +
第三方审计记录"。任何"我们自己宣布通过"的口径都不再使用。**
