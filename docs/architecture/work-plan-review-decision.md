# 工作安排审查裁决（问题描述-01）

> 审查对象：问题描述-01-工作安排算不算长期记忆.md（2026-11-14 至 11-19 真实使用，已脱敏）
> 裁决者：本项目架构设计的 外部架构顾问 模型（独立判断，不迎合预设，不机械接受 ChatGPT 参考意见）
> 裁决原则：每个问题给「行/不行」+ 理由；两者都有时各自指出成立部分；考虑正反例避免误伤。

---

## 总判断（先说结论）

A–E 五条记忆**都不该进入个人长期记忆库**。用户「这属于某次工作安排，不属于长期记忆」的判断方向正确，但理由需要精确化：**不是因为「持续时间短」（它们持续了数天），而是因为「描述对象是一次性协作的安排/评价，不是跨情境稳定的用户属性」**。

「持续时间」是错误判据——它会把「用户喜欢结对编程」这类真偏好漏掉，也会把「某次三周项目用了 pnpm」这类临时安排误留。正确的判据是「**描述对象 + 跨情境稳定性**」。

---

## Q1. 「工作安排」与「长期记忆」的边界在哪？

**裁决：不行（A–E 不属于长期记忆）。**

一句可执行判据（≤40 字）：

> **记「跨情境稳定的用户属性/偏好/长期状态」；不记「某次情境的安排或评价」，能从文件查到的也不记。**

三个反例检验（它们形式接近但答案不同，区分点在于「描述对象」与「跨情境稳定性」）：

| 例子 | 裁决 | 理由 |
|---|---|---|
| 「用户决定下个项目用 Rust」 | 行 | 描述对象是**用户的技术偏好/倾向**，跨项目稳定，是 profile |
| 「本项目用 pnpm 不用 npm」 | 不行（进项目文档，不进记忆） | 描述对象是**某个项目的配置**，可从项目文件验证；即便长期，也应走 domain 文档而非个人记忆 |
| 「报告写得完整而非简洁」 | 行 | 描述对象是**用户的稳定表达偏好**，跨项目成立，是 profile |

区分它们的到底是什么：**「这句话的主语是『用户这个人』还是『某次任务/某个项目』」+「下周、下个项目它还成立吗」**。A–E 的主语都是「这次协作/这个协作看板机制」，下周就废弃了，所以不是长期记忆。

## Q2. 「能被验证」是否应成为准入条件？

**裁决：两者都有（c）。**

- **写入侧判据缺失（成立）**：既有规则只有「能从文件看出来的不该记」这一条原则，但没有把它做成**写入时的强制准入检查**，也没有「工作安排/协作配置」这一排除项。执行侧当时不违规，是因为规则本身没这条。
- **这类信息本就不该走记忆通道（成立）**：协作约定、分工、机制评价是「项目状态/运行时配置」，正确归宿是项目文档与状态文件，不是「个人长期记忆」。

所以不是二选一，而是同一根因的两面：**记忆系统与项目文档的职责边界不清（呼应台账 #47 运行时状态污染）**。修法是把「可从文件验证 → 拒绝写入」和「一次性安排/评价 → 拒绝写入」做成写入准入闸，而不是只靠原则。

## Q3. 「纠错型记忆」是不是反模式？

**裁决：是反模式，不值得单独存。**

D 的唯一用途是纠正 C。但「某条事实已失效」这件事，正确表达方式是**改 C 自身的状态**（superseded 或 deleted + superseded_by 指向），而不是新增一条 active 的负向记忆 D。

理由：负向记忆（「不要做 X」「X 已废弃」）没有独立信息价值，只有「旧事实已失效」的元信息价值；而元信息应该挂在被失效的那条上。D 的独立存在还带来 Q4 的指代词污染（纯负收益）。

正确做法：**删干净 C，不留替代条目**；如果纠正后产生了新的当前事实（如「新分工是 Y」），才写 Y；否则什么都不写。

## Q4. 指代词污染怎么处理？

**裁决：选 (a)，禁止记忆正文出现指代词；不选 (b)。**

- **(a) 成立**：记忆是跨窗口共享的，正文必须「脱离上下文可读」。禁止「本窗口/这里/刚才/上次」是指代，本质是**强制写入者把信息抽象成独立成立的表述**——这个抽象过程天然过滤掉大部分会话级工作安排（因为它们往往只能用指代表述）。
- **(b) 会破坏核心价值**：加会话作用域，等于把「跨会话个人记忆」退化成「会话快照」。用户明确希望「他是谁、怎么被称呼」在所有窗口成立——这些真正有价值的全局事实，一旦引入会话作用域，就要额外区分「全局 vs 会话」，复杂度大增且易误伤。工作安排的正确归宿是**项目文档/状态文件**，不是「带会话作用域的记忆」。

补充：指代词的存在本身就是一个强信号——「一条记忆如果必须用『本窗口/这里』才能说清，它大概率是会话级信息，不该进长期库」。禁止指代，等于把这条信号变成硬规则。

## Q5. 失败的责任在哪一层？

**裁决：产品规则不完整（缺少排除项），不是执行侧失误，也不是用户冲突。**

- 执行侧**没违规**：规则里没有「工作安排不许记」，系统据实写入，无可指摘。
- 用户表达**没冲突**：用户说「记住我们这样协作」，系统记了——冲突是用户事后才意识到的（「协作安排」本身不该是记忆系统的对象）。
- 根因是**规则缺了「什么不记」的排除项**：没有「一次性工作安排/协作配置」排除项，没有「可从文件验证则拒绝」的强制准入。

所以责任在**产品规则层**：记忆系统只定义了「记什么」，没定义「不记什么」。这也是台账 #47（运行时状态污染、task scope 零使用）的同一根因——缺一道写入准入闸。

## Q6. 全局共享记忆是否允许「本窗口/这里/刚才」等上下文依赖性指代？

**裁决：不行。**

全局共享 + 无会话维度（检索只按 user_id 过滤）意味着：任何窗口检索到含「本窗口」的记忆，都会把它读成「说我」。这类指代无法脱离上下文独立成立，违反「记忆必须可脱离上下文阅读」的基本要求。允许它，就等于允许一条记忆在不同窗口有不同含义——这在共享库上就是确定性污染。

## Q7. 当前系统是否存在跨窗口污染风险？不增加窗口隔离，能否安全容纳窗口级工作安排？

**裁决：存在污染风险；不能安全容纳。**

- **存在污染**：一条窗口级记忆（含「本窗口」或语义上是「某窗口的角色」）被其他窗口检索到，会被错误解释成「说我/我该这么做」。台账 C 类「某窗口是执行方」就是活例——另一个窗口读到它，会误以为「自己是执行方」。
- **不增加窗口隔离，无法安全容纳**：工作安排天然是会话级、临时的、可从文件验证的，与「全局共享、跨会话稳定」在三个维度上都矛盾。强行塞进全局库，要么污染（含指代），要么误伤（把真全局事实降级）。

**正确归宿**：工作安排走「项目文档/状态文件」或「会话级上下文」，不进全局记忆库。若要支持窗口级记忆，那是另一套「会话作用域」机制——但会破坏核心价值（见 Q4），所以**不做**。

## 额外交付（问题描述 §4 要求）

**1. 可写进提示词/规则的判据（≤40 字）：**

> 记跨情境稳定的用户属性/偏好/长期状态；不记某次安排或评价，能从文件查的也不记。

**2. 反例（按判据会误删/误留什么）：**

- **会误删（判据过严的代价）**：若把「用户对协作方式的一次性评价」误判为「稳定偏好」——如「用户不喜欢低效协作」本可以是 profile，但若只是对「协作看板」这一具体机制的评价，判据会正确拒绝它；真正的风险是**误删「已固化为长期约定的工作偏好」**（如「用户坚持每周五站会」），这需靠「跨情境稳定」这一修饰词兜住——凡跨情境、反复出现、下周仍成立的，即便带「工作」字样也照记。
- **会误留（判据过松的代价）**：若只看「描述用户」，会误留「用户认为协作看板削弱效率」（E）这类对具体机制的评价；它形式上像偏好，实为一次性评价。所以判据必须同时要求「跨情境稳定」，才能挡住 E。

**3. 五条里有没有该保留的？**

**没有。** A（协作约定）、B（暗号）、C（窗口分工）都是纯协作配置，D 是纯纠错（反模式），E 虽最接近「偏好」但仍是「对某次机制的一次性评价」，均不满足「跨情境稳定」。唯一需要保留的不是某条记忆，而是**「用户偏好低效协作会主动废弃」这个 profile**（如果未来反复出现同一模式，才值得作为稳定偏好记入）——当前证据不足以记。

## 本裁决对设计书的意义

- 支撑「写入意图准入门」（V1-2）：新增两条确定性排除规则——「可从文件验证 → 拒绝」「含上下文指代/一次性安排 → 拒绝」。
- 支撑「职责分层」：工作安排/协作配置归「项目文档/状态文件」，不进「个人长期记忆库」。
- 支撑「记忆作用域」结论：维持全局共享，**不引入会话作用域**，靠「禁止指代 + 准入闸」解决污染，而非靠作用域隔离。
